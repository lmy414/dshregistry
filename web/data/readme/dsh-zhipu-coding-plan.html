dsh-zhipu-coding-plan

English | 中文

A DeepSeek Harness web plugin: your Zhipu GLM Coding Plan quota and usage as a fourth conversation view tab (额度), beside 对话/轨迹/统计. The host half queries the Zhipu monitor API (the same three endpoints the official usage plugin reads) through one Connection RPC channel; the browser half renders the windows — no service or store mutated on the harness side.

Install (one command)

dsh plugin --profile web add dsh-zhipu-coding-plan

Then (re)start dsh --profile web and open the URL; the 额度 tab appears at the end of the conversation tab strip. Uninstall with dsh plugin --profile web remove dsh-zhipu-coding-plan.

Before this package is published to a registry, install from a checkout or a git URL instead:

dsh plugin --profile web add /abs/path/to/this/checkout
# or
dsh plugin --profile web add github:tsja2001/dsh-zhipu-coding-plan

What the tab shows

  • Quota windows — the plan's limit rows as cards: 5-hour tokens, weekly tokens (classified by the API's unit field, never by reset time), and the monthly MCP tool quota with used/total/remaining plus per-tool details. Used percentage renders as a ratio bar; ≥80% turns warn, ≥95% error. Each card shows the window's reset countdown.
  • Model usage (switchable 近24小时 / 近7天 window) — call count, token total, a per-bucket sparkline, and per-model share rows (top 8, then "+N more").
  • Tool usage — network search / web read / Zread / search MCP counts over the same window.
  • API key management — the panel configures itself: save the key from the tab (validated against the monitor API before it is stored; a wrong key never reaches storage), or fall back to the documented environment variable. The key source (credential store vs environment) is shown, never the value.

Data refreshes on load, on window switch, on demand, and every 2 minutes while the page is visible; host results are cached ~30 s per window with in-flight deduplication.

API key resolution

The plugin consults the harness credential layers under the reference ZHIPU_API_KEY (configurable, see below), re-resolving on every refresh so rotation needs no restart:

  1. the launching environment (export ZHIPU_API_KEY=…, highest priority),
  2. the harness credential store (~/.dsh/.credentials.yaml, written by the tab's save form — what the web Models page uses),
  3. .env in the launch directory, then $DSH_HOME/.env.

A key that works for inference elsewhere (DeepSeek, OpenAI, …) is not a Zhipu key: the panel reports it as rejected with a hint instead of failing opaquely. Personal plans only — team-plan query headers are not implemented.

Configuration

The inserted row carries no config; defaults live in the plugin schema. Override by row id from any user patch layer (profile cordis.patch.yml, $DSH_HOME/cordis.patch.yml, or --patch):

- id: zhipu-coding-plan
  config:
    apiKeyEnv: ZHIPU_API_KEY   # credential reference to resolve
    baseURL: https://open.bigmodel.cn
    cacheTtlMs: 30000          # refresh cache per window
    timeoutMs: 20000           # per-request timeout

Disable the tab entirely with - id: zhipu-coding-plan, disabled: true. Remember a patch replaces the row's whole config — restate every key you need.

Requirements

A dsh web profile whose browser roster includes the standard client packages (the stock web profile does), with dsh-client-connection present — it is. The tab appears only when the web server serves the plugin's lib/client.js; if it is missing after install, restart dsh --profile web (the client graph composes at boot).

Error handling

Failures carry a stable kind end to end; the panel localizes them instead of showing raw transport text: missing key, invalid/non-Zhipu key (detected on both the HTTP status and the API's code: 401 envelope — the latter is how Zhipu actually reports it), rate limited, server error, network/timeout, and non-JSON (proxy interception). Usage-detail endpoints degrading never hides quota figures — a muted note explains; stale data stays visible under the error banner.

Repository layout

  • src/ — plugin sources: host half (index.ts, zhipu.ts, shared protocol.ts), browser half (client/)
  • lib/ — prebuilt bundles installs consume (refreshed by node scripts/build.mjs against a harness checkout)
  • cordis.patch.yml — the profile layer this package contributes (dsh.bundle)
  • scripts/build.mjs — typecheck + bundle both halves, borrowing the toolchain from a deepseek-harness checkout (DSH_CHECKOUT=… , default ../deepseek-harness)

Model Experience

The plugin's host half issues GET requests to open.bigmodel.cn monitor endpoints on refresh (quota, model usage, tool usage — no inference requests); the browser half renders results and reaches no model.

KV Cache effect

None; the monitor endpoints are usage queries and carry no conversation context.

Known Limitations

  • Personal plans only; team-plan query parameters (?type=2 + organization headers) are not implemented.
  • The monitor API reports token windows as percentages only — absolute token counts for those windows are not available.
  • The two usage endpoints are undocumented; the mapping follows the official usage plugin and degrades gracefully when they change.
